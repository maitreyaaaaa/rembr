# Reference support-code and delivery coverage

## Scope and method

Read-only source review of tracked support code outside `apps/ui`, `apps/orchestration/src|test|supabase/migrations`, and `extensions/save-to-iscraper`. The reviewed implementation paths are listed below with current behavior, branches, and known verification limits. `scripts/apply-supabase-migration.js` can mutate a connected Supabase database; it was read only and not invoked. Load runners and probes were not executed. No tests, database queries, deployments, or other external side effects were run.

REA separately statically analyzed 181 tracked JS/TS paths. Its bounded structural result and limits are recorded in `rea-static-analysis.md`; the static graph does not replace this source map.

## Operational scripts (7)

| Tracked path | Functions / branches traced | Risks, limits, and Rembr design notes |
|---|---|---|
| `scripts/apply-supabase-migration.js` | Reads positional migration path or env/default; loads existing root/Vercel/workspace env files without overriding process env; derives project ref from explicit ref or Supabase URL; POSTs SQL to Supabase Management API; then runs one of several migration-specific read-only verification SQL queries, with a generic export-schema fallback; redacts token/JWT patterns in API error text; exits nonzero when apply/verification fails. | **External mutation capability.** Applying SQL occurs before verification and has no automatic rollback. The default target is the user-data-export migration. If a caller supplies a different migration without a special verifier, fallback verification still checks export-schema objects, so success/failure may not reflect the selected migration. It also accepts an absolute path. Rembr should require an explicit project and migration, show a dry-run/approval diff, verify checksums/allowlisted migration location, maintain a migration ledger, and implement a matching verifier before any live apply. Never invoke with production credentials without a separate deployment approval. |
| `scripts/authenticated-load-runner.js` | Resolves base URL/profile and Supabase URL/anon key/test-user credentials from env; signs in a dedicated password user; classifies auth/network/status errors; times profile/items/search preflight and refuses to start k6 unless all are HTTP 200; starts `npm run load:auth` with access token only in the child process environment; catches and categorizes errors without printing credential values. | It reads a test user's password and obtains a live bearer token; only use dedicated synthetic accounts and an explicitly selected environment. Preflight is read-only; the k6 harness has an optional mutation scenario controlled by a second opt-in. External API/k6 behavior was not tested here. |
| `scripts/region-probe.js` | Parses comma-separated target env or default production target, caps repetitions to 1–20, probes `/api/health`, measures latency, collects status/cache/request/`x-vercel-id`, summarizes edge/function regions, optionally prints JSON, exits nonzero on 5xx/network failure. | Public health probe only: does not establish authenticated data-path latency, residency, database location, or representative workload. The default targets the production origin, so any run is an external request. Prior report measurements are historical. |
| `scripts/route-inventory.js` | Scans sorted route files; regex-detects direct literal `app.get/post/put/patch/delete` declarations; heuristically classifies access, scans bounded source context for auth helpers/limiters/body limits/output risk, renders Markdown and validates expected route auth and selected rate-limit expectations. Exports pure helpers for tests. | Regex/source-window classifier is not an AST or runtime route proof: dynamic paths, mounted routers, multiline syntax, control flow, wrapper semantics, and omitted limit patterns can be missed or misclassified. Treat as a review index and compare every emitted route with the handler audit, not as authorization enforcement. |
| `scripts/security-boundary-check.js` | Recursively scans UI `src`, existing UI `dist`, and extension files for server-only secret names/prefixes; scans selected text extensions; skips directories named `node_modules` and `scripts`; reports file/line/name and exits on matches. | Checks known secret-name markers, not real leaked values, entropy, secret variants, generated deployment bundles, source maps, or all paths; broad patterns can flag innocuous text. The `scripts` exclusion can omit a future browser-facing scripts directory. Use alongside secret scanners and bundle inspection. |
| `scripts/supabase-db-audit.js` | Loads env files; requires management token/project ref; submits read-only SQL for RLS/policy, hot-table index and aggregate table statistics inventories; runs `EXPLAIN (ANALYZE false)` on fixed synthetic deletion lookup, first-page list and candidate keyword search; summarizes plan nodes, relations/indexes/cost/rows; recommends reviewing draft indexes based on fixed names; prints a sanitized report. | Reads live database metadata/query plans if invoked; it is not a migration or row-level security test, and synthetic UUID/text values plus a small fixed query set do not represent real workload. Index advice is heuristic. Never run without an explicit environment and authorization. |
| `scripts/supabase-security-check.js` | Reads/sorts migration SQL, normalizes comments/whitespace, regex-parses table definitions, RLS enables, policy statements, grants/revokes, storage bucket settings, ownership policies, selected composite tenant FKs and nearby `SECURITY DEFINER`/`search_path`; compares against a server-only and intentional-anonymous allowlist; reports findings/review rows and exits status. | Static regex analysis can miss SQL constructs, split statements, role ACLs, function overloads, SQL-language functions, later changes in live DB, or semantic policy defects; nearby-window parsing is brittle. A pass is not proof of effective hosted ACL/RLS. Continue with migration-specific review and live ACL inspection. |

## Load-test and region scenarios (3)

| Tracked path | Scenario and assertions | Safety/interpretation |
|---|---|---|
| `tests/load/iscraper-authenticated.js` | k6 constant-arrival scenarios for profile read, library browse, indexing summary, no-AI search; optional `manual_link_save` scenario only when `AUTH_MUTATION_ENABLED=true`. Defaults are low-rate 20s readonly; profiles can override rates/duration. Counters distinguish 401/403/428 from ordinary failures; thresholds cover request failures, p95/p99 and invalid auth. Each action checks expected status and sleeps. | Requires explicit `AUTH_TOKEN`; use only a dedicated test-user session. Mutation branch persists synthetic links and is opt-in; should target disposable test data, not production user libraries. HTTP statuses through 499 are treated as expected by k6 so custom `check` assertions determine failure. Thresholds are targets, not measured proof. |
| `tests/load/iscraper-mixed.js` | Mixed constant-arrival profile for public health, library browse, synthetic Instagram-like HTML upload import, no-AI search, and admin worker status; local/deployed/warmup/custom defaults vary rate/VUs; optional bearer token or development-only user headers; admin key if configured; checks accepted auth/throttle/failure statuses and latency. | Import scenario is always present and creates test work/data; do not point at production. `X-User-ID` fallback depends on server dev/local trust behavior and should not be considered authenticated load. Missing admin key is expected to lock status route. This test mixes routes with different identity semantics, so report profiles and auth validity precisely. |
| `tests/load/iscraper-region-probe.js` | k6 public health probe over comma-separated targets, configurable duration/rate, validates 200, request-ID and Vercel routing headers, failure-rate and latency thresholds. | Checks response/routing metadata only. It cannot prove application data locality or compare regions without controlled target pairs and repeated authenticated traffic. A multi-target loop increases request volume per VU. |

The load tests were read but not run. Existing reports in `docs/phase-6*` are historical artifacts and need current environment, source revision, valid credentials, workload, region, and warm/cold details before reuse.

## Verified vs unverified

- **Source-confirmed:** scripts and manifests contain the behaviors above; they were inspected statically.
- **Not performed:** no test, k6 run, Supabase Management API request, production load, migration, deployment, extension runtime test, browser check, or credential lookup.
- **Not established by source:** current live Vercel/Render revisions/config, secret values, Supabase applied migration state/effective ACL, paid plan entitlements, browser store status, and measured live reliability.
