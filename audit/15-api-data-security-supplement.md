# API and data security supplement

Expanded continuation review of API route wiring, authentication special cases, account creation, AI consent paths, migration RLS declarations, and stored-data/third-party processing. No production credentials or service data were read.

ID: SEC-001 | Severity: High | Confidence: CONFIRMED
Location: apps/api/src/app.ts:L137-L147; apps/web/src/App.tsx:L109-L123; apps/web/src/components/SupportPages.tsx:L104-L108
Problem: Registration accepts only the Terms checkbox, but it creates four AI preference rows as enabled and records the current disclosure versions and `consented_at` timestamp for AI analysis, AI search, visual search, and semantic search. The Terms page explicitly says its policy is still being prepared; there is no separate user action or disclosure acceptance in the registration request. The API and tests consequently treat this seeded value as valid opt-in.
Evidence: `app.ts:138-147` stores `terms_accepted_at` then inserts each preference with `enabled=TRUE` and a current disclosure version plus timestamp. `App.tsx:112` submits only `acceptedTerms`; `App.tsx:122` renders the signup form and Terms checkbox. `SupportPages.tsx:104-108` states the terms page is in preparation. `phase-three-ai-routes.test.ts:9-25` names the behavior “Terms acceptance enables AI media analysis by default” and asserts the preference is true; `visual-search.test.ts:115` and `semantic-search-routes.test.ts:77` also assert enabled defaults. The AI worker selects work only when the preference row is enabled with the current disclosure version (`apps/api/src/ai/worker.ts:110-116`). Import acceptance can queue AI analysis jobs (`apps/api/src/imports/repository.ts`, see its consent-gated enqueue query). The settings APIs separately require the caller to send the current disclosure version when enabling these features (`apps/api/src/ai/routes.ts:28-35`; semantic equivalent in `apps/api/src/library/semantic-routes.ts`).
Impact: A new account is recorded as having consented without an affirmative AI-specific choice. Imported media may be sent to the configured external analysis provider automatically; AI-assisted search or visual/semantic flows may also transmit user content or query text after the user invokes them. The published UI does not provide the policy details at signup, so a user cannot make the recorded choice based on the represented disclosure.
Fix: Default all AI-related preferences to disabled and leave consent version/timestamp null at account creation. Require a separate, explicit, feature-specific acceptance through the existing preference endpoints before any provider processing. Update default-consent tests to prove no work is queued or transmitted until explicit consent.
Tier: 1 | Effort: S | Risk of fix: Low | Depends on: none

## Additional evidence and scope

- The route inventory contains 72 HTTP declarations across `apps/api/src`; app-level public routes are health, register/login, demo session issuance (only when a configured active owner exists), and logout. Most feature routers mount `requireUser` and profile middleware. `/api/v1` uses scoped API-key middleware and a per-key rate limiter. MCP validates bearer JWT issuer/audience and maps the authenticated WorkOS subject to an active, linked owner before constructing owner-bound tools. No unauthenticated owner-data route was found in the reviewed routers.
- Migrations create 50 tables over the history; 49 surviving tables have `ENABLE ROW LEVEL SECURITY`. The only table without a matching enable declaration is legacy `processing_jobs_v1`, which is created and dropped within the initial migration. The app uses server-side database credentials, so migration RLS is defense in depth; hosted grants/RLS role behavior still requires live verification. No `GRANT` or `SECURITY DEFINER` declaration was found in migrations.
- Routes generally pass the authenticated `req.user.id` to repository/service methods, and SQL uses placeholders for user-controlled values. The MCP audit table name is a fixed constant. This was a pattern review; it is not proof that every SQL query in all 69 API source files is correctly owner-scoped.
- This supplement does not establish hosted provider configuration, actual account defaults in production, third-party execution logs, SQL grants, or legal adequacy. It adds one confirmed source-level finding missed by the initial bounded review and supersedes that review’s blanket “no Medium/High security finding” summary for AI consent defaults.
